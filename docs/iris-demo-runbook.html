Recording script · Iris for Claude Code

Iris Demo Runbook

A seven-scene walkthrough that takes a viewer from “my agent costs something, I don’t know what” to a published change and a blocked command — using only numbers Iris measured from real traffic.

7 scenes ~9 min runtime 1 browser tab + 1 terminal Iris on :8787

Before you hit record

Every failed demo of this product fails the same way: the dashboard is empty, or it shows one degenerate call. Both are fixable in two minutes.

Iris is running in the project you’ll demo
From the project directory: node bin/iris.mjs. The header chip should read project · recording with a green dot.
Guard hooks point at the copy you’re demoing
Check .claude/settings.json → hooks. If the command path contains .npm/_npx/, your hooks run the published Iris, not your working tree — so any Guard change you just made won’t appear. Re-run iris init from the checkout to re-point them.
The authority envelope has a task written on it
An accepted envelope with an empty task field makes Scene 6 look unfinished. Open Guard, type the task, click Accept envelope before recording.
Warm the capture with a real agent turn
Run claude and ask it something that uses tools — “read the README and summarise it” works. A turn carrying the full tool array is what makes Optimize meaningful; background utility calls carry no schemas and will leave the page looking broken.
Set the header range to Today
The range filters every view. Last hour is the most common reason a page looks empty mid-demo.
Don’t clear the capture
The Clear captured data link in the sidebar footer wipes proxy-logs/, the spend ledger and the action log. There is no undo.

The story you’re telling

Pick one narrative and hold it. This one works because each page answers the question the previous page raises.

The setup: you’ve been using Claude Code on a real project for a few weeks. It works. You have no idea what it costs, what it’s carrying, or what it’s allowed to do — and none of those are visible from inside the tool.

The arc: see it → price it → cut it → constrain it → prove it. Overview and Traffic make the traffic visible. Spend prices it from reported usage. Context shows what’s filling the window. Optimize turns that into a change you publish. Guard bounds what the agent may do. Flight Recorder is the receipt.

The line that lands hardest

Iris sits between Claude Code and the API, so everything on screen is measured off the wire — not estimated, not sampled, not reported by the thing being measured.

The seven scenes

Do is what you click. Say is narration you can read aloud. Watch is what to make sure is on screen before you move on.

1 Overview — what a session actually did ~60s · key 1
Do
Open 127.0.0.1:8787/__monitor. Land on Overview. Let the KPI row and the ribbon fill.
Say

This is a real Claude Code session, recorded as it happened. Iris runs as a local proxy — every request the agent makes passes through it on the way to Anthropic.

Five numbers across the top: how much context was shipped, what it was billed, how much of it was tool schemas nothing called, whether an authority envelope is in force, and what Guard decided.

Watch

The ribbon — “the payload, drawn to scale” — needs a live call to render. If it says ledger row, the browser was reloaded after those calls; run one more turn and it comes back.

2 The ribbon — one turn, drawn to scale ~50s · hover
Do
Hover slowly across the ribbon, left to right. Pause on a tool-schema band. Point out a dashed cache-breakpoint notch.
Say

Every pixel here is a token that left this machine on one turn. Blue is the system prompt, gold is tool schemas, violet is the conversation.

The dashed lines are cache breakpoints. Everything to the left of one gets re-sent every single turn — which is the whole reason tool schemas cost what they do.

Watch

The tooltip shows tokens, cost per turn and cost per month for the band under the cursor. That per-month figure is the hook into Scene 5 — say it out loud.

3 Traffic + the call inspector ~90s · key 3, then click a row
Do
Press 3. Click the row with the largest token count — the drawer opens on the right. Scroll it. Expand System prompt, then Tool schemas, then Conversation. Use j / k to step between calls.
Say

Every call the agent made, with what it carried and what it cost. Click one and you get the inspector.

Top of the drawer is the invoice — input, cache read, cache write at five minutes and at one hour, output, thinking tokens. Each line is tokens times the rate that category actually bills at, so you can check the arithmetic yourself.

Below that is the payload itself. This is the full system prompt Claude Code sent — every block, with the cache breakpoints marked. Most people have never seen it.

Then the tool schemas, ranked by size. Then the whole conversation, message by message, including the thinking blocks.

Watch

The system prompt block is the single most memorable thing in the demo. Scroll it slowly enough that the viewer registers how long it is. If it’s empty, you clicked a ledger row rather than a live call.

4 Spend — measured, not estimated ~70s · key 2
Do
Press 2. Walk the KPI row, then the per-day table. Stop on Cache expiries.
Say

This is priced from the usage the API reported on each response — not estimated from token counts. Calls whose model isn’t in the price book are excluded rather than counted as free.

The one worth pausing on is cache expiries. Step away for longer than the cache lifetime and your next call reprocesses the entire context at write price instead of reading it back at a tenth of input. Iris shows you what those idle gaps cost — and it reads the lifetime off the TTL each write actually used, so it holds whichever plan you’re on.

Watch

Now click the billing-mode chip in the header. This is the moment to make the point below about what the dollars mean.

5 Billing mode — why the numbers are believable ~60s · header chip + ? key
Do
Click the mode chip in the header. Show the four modes. Switch Subscription seat → Console API key and let the viewer see the figures re-label. Switch back. Press ? for the pricing explainer, scroll it, close it.
Say

Here’s the thing most cost tools get wrong. Claude Code meters the same tokens four different ways, and Iris reads which one you’re on from the credential shape on the wire — never the credential itself.

On a Max seat you pay a flat fee, so a dollar figure isn’t a bill. Iris says so: it leads with tokens and share of your metered usage, and puts the dollars in brackets as what this traffic would cost the moment you pass your allowance and usage credits start charging per token.

Switch to an API key and the dollars become the headline, because now they’re literally your invoice. On Bedrock or Vertex it drops the dollar columns entirely rather than pricing your traffic off a rate card that doesn’t apply.

Watch

The help sheet has a “What Iris cannot tell you” section. Land on it. Saying out loud what the tool doesn’t know buys more credibility than any number on the page.

6 Optimize — cut the tool tax, publish it ~110s · key 5 · the payoff
Do
Press 5. Read the KPI row. Point at On but unused. Click Stage N changes — watch the header counter increment. Scroll a group table and toggle one tool by hand. Then click Publish changes. Cut to the terminal and cat .claude/settings.json.
Say

Tool schemas ship on every single turn, whether the agent uses them or not. This page counts which ones were never called.

The rate isn’t list price — a schema sits inside the cached prefix, so from the second turn it bills at the cache-read rate. Pricing it at list would overstate this tenfold. The turn count is measured from your own capture, with idle gaps over five minutes excluded so lunch doesn’t drag your pace down. The working pattern is the one assumption, and it’s a control you can change right here.

Stage the unused ones, publish — and that writes to the deny list in your project’s settings. Next Claude Code session, those schemas don’t ship.

Watch

Cutting to the terminal to show the deny list actually change is the strongest beat in the demo — it proves Iris writes real config rather than keeping a private opinion. Core tools are locked by default; flip Let me switch off core tools too only if you want to show the guardrail.

7 Guard + Flight Recorder — what it may do, and what it did ~150s · keys 6 and 7
Do
Press 6. Show the may / may-not lists and the accepted envelope. Cut to the terminal, run the three commands in the next section. Cut back — decisions appear in the right-hand column. Press 7 for Flight Recorder, click a row to expand it.
Say

Guard is the part that isn’t about money. The model proposes what this task needs; you accept it; Iris enforces it from outside the conversation. The model can propose an envelope — it cannot widen one.

This runs as a PreToolUse hook, so the decision happens before the tool executes. And it evaluates effects, not command strings — what this actually does, to what, in which environment.

Three outcomes. Inside scope, it runs. Destructive but recoverable, it asks. Production, or destructive outside your project — denied, and the decision is logged with the rule that fired.

Flight Recorder is the receipt: every action that ran, in order, with what Guard decided about it. Shell writes are flagged. Click any row for the full command.

Watch

Guard decisions only appear if the PreToolUse hook is installed and pointed at the copy you’re running. This is the checklist item that most often bites.

The Guard demo, specifically

You asked what to show here. These are the three tiers with commands taken from Iris’s own policy test suite — so they behave exactly as written, against the default envelope: filesystem $PROJECT/**, environments staging, production deny, destructive ask.

ALLOWinside envelope scope

Editing files inside the project, running tests, local non-destructive tools. No prompt, no friction — the point is that Guard is invisible until it isn’t.

npm test
edit any file under the project root
ASKdestructive · unknown · external write

Recoverable, or not confidently classifiable. Guard stops and puts the decision in front of you rather than guessing. Note that a push to main asks rather than denies — the envelope is about consequence, not ceremony.

rm -rf /tmp/stuff
find . -name '*.log' -delete
git push --force origin main
python3 deploy.py
npx create-thing@latest
DENYhard rule · no prompt offered

Production, production credentials, or destruction outside the project. These don’t ask, because a prompt you can click through isn’t a boundary.

deploy --env production
railway volume delete v --environment production
Do not type a real destructive command on camera

The two DENY commands above are safe to demo because neither tool is likely installed and neither target exists — if Guard were somehow bypassed, nothing happens. Iris also denies things like rm -rf /etc, and that is worth saying. It is not worth typing into a live shell that a misconfigured hook might not be watching.

The three lines that carry Guard

If you cut everything else, keep these:

“Discovery does not grant authority. The agent finding your production credentials doesn’t mean it may use them.”

“It evaluates effects, not strings — so it isn’t a regex blocklist you can talk your way around by rephrasing the command.”

“And it catches accidents and drift, not a model deliberately working around it. That distinction is written into the product, not glossed over.”

The trajectory angle, if you have time

Guard also tracks paths across a session, not just individual calls — staging drifting toward production, reads escalating to destructive operations, credential scope widening, recovery depth climbing after repeated failures. Signals show at the top of the Decisions column. It’s a strong closing beat because no single call in the sequence looks alarming on its own.

Page-by-page cheat sheet

For the “what does each page do” pass, or a written description under the video. Number keys switch views.

1Overview
Five KPIs, the ribbon, cost-per-call chart, and the signals Iris flagged. Where you start and where you return.
2Spend
Measured cost per day and per model, cache economics, and what idle gaps cost when the prefix had to be rebuilt.
3Traffic
Every call in a table. Click any row for the inspector — invoice, system prompt, tool schemas, conversation.
4Context
What fills the window on one turn, split five ways: breakdown, system prompt, tool schemas, conversation, and what changed since the previous turn.
5Optimize
Which schemas ship and which were never called, what that repeats to per month, and a stage-then-publish flow that writes the deny list.
6Guard
The authority envelope — may / may not — plus every PreToolUse decision with the rule that fired.
7Flight Recorder
Every action that actually ran, newest first, filterable by tool. Shell writes flagged. Click to expand.
⌘KCommand palette
Jump to a view, a call, a tool, or an action. Worth two seconds on camera to show the surface is navigable.

If something goes wrong mid-take

What you seeWhyFix
“Nothing is reaching this proxy” Your agent’s ANTHROPIC_BASE_URL points at a different port than Iris bound. The banner names both ports. Restart Iris on the port settings.json expects, or fix the file.
“Waiting for the agent…” Wiring is correct; nothing has run yet. Run a turn in the project.
“Nothing in this range” Header range excludes your calls. Switch to Today or All.
Ribbon blank, row says “ledger row” Payload text lives in memory; the page was reloaded after those calls. Run one more turn. The bodies are still in proxy-logs/, but nothing reads them back yet.
Optimize shows everything blocked No tool schemas captured since Iris last started — the schema store is in-memory, so the list falls back to the deny list alone. Run a turn that uses tools. Don’t restart Iris again before recording.
No Guard decisions Hook missing, or pointing at a different Iris install. Check hooks in settings.json; re-run iris init from the copy you’re running.

Commands in the Guard section are drawn from tests/guard.test.mjs, so they match the shipped policy engine. Everything else describes the dashboard as built. Re-check the two flagged setup items after any restart — both were live in this workspace when this runbook was written.
